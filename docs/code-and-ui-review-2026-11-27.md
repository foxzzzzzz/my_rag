## 一、结论摘要

- **代码中存在 5 项明确问题**：1 项历史版本清理偏差，4 项边界条件或交互可靠性问题。
- **UI 不需要推倒重做**。现有灰蓝中性风格、阅读宽度和信息密度总体合理，建议优先优化移动端审核、问答首屏、操作反馈和触控目标。

## 二、代码问题

### 1. 高：历史版本清理可能删错“其他旧版”

**代码位置**：`personalkb/version_retention.py:15-23`  
**规则依据**：`docs/version-history-retention.md:5,11`

当前逻辑先保留最近 N 份达标批准旧版，再把**超额批准旧版也归入 `others`**，占用“其他历史版本”的保留名额。

触发示例：`approved_history=1`、`other_history=1`，历史版本从新到旧为：

```text
批准 A3、批准 A2、批准 A1、返工 R1
```

- **预期**：保留 A3、R1，清理 A2、A1。
- **实际**：A2 占用“其他旧版”名额，R1 被清理。

**影响**：自动维护会删除不符合保留策略的版本正文和证据。清理前有冷备，降低了不可逆风险，但仍属于实质性的保留规则错误。

**修复建议**：

- 分别计算 `keep_approved` 和 `keep_others`。
- 最后清理“不在两个保留集合中的全部历史版本”。
- 补充“多份超额批准旧版排在其他旧版之前”的测试；现有测试未覆盖该组合。

### 2. 中：多个轮询可叠加，详情响应还可能旧覆盖新

**代码位置**：

- `web/src/main.jsx:263-274`
- `web/src/management.jsx:103`
- `web/src/favorites-panel.jsx:122-129`

这些位置使用 `setInterval` 直接发起异步请求，请求时间超过轮询周期时会叠加。

其中详情轮询只有页面导航序号，没有请求序号：

1. 请求 A 先发出，读取旧详情。
2. 请求 B 后发出，先返回新详情。
3. A 最后返回，`syncDetail()` 在同一版本下仍会调用 `showDetail()`，把新详情覆盖成旧详情。

资料列表的 `refreshOrder` 已有一定保护，但不能解决详情、收藏和抖音任务的竞态。

**影响**：慢网络或服务响应延迟时，可能出现重复请求、界面状态回退，以及详情数据被旧响应覆盖。

**修复建议**：

- 统一改为“上一次完成后再 `setTimeout`”的串行轮询。
- 为每类视图增加请求序号，只允许最新请求更新 UI。
- 使用延迟 Promise 测试“A 先发起后返回、B 后发起先返回”的场景。

### 3. 中：问答费用授权跨操作保留，不符合“本次明确同意”

**代码位置**：`web/src/rag.jsx:12,78-114,217-220`  
**规则依据**：`docs/phase-3-rag-guide.md:3-5`

`paid` 被用于请求的 `allow_paid`，但 `run()` 完成或失败后没有重置。结果是：

- 一次勾选后，可连续生成多次回答，无需重新确认。
- 切换问题或离开问答页再返回，授权仍可能保留。

这与“混合检索/回答/建索引仍需**本次明确同意**”不一致，也增加了误触发后续付费请求的可能。

**修复建议**：

- 每次检索或回答结束后清除授权。
- 下一次点击付费操作前必须重新勾选。
- 不要自动重发结果未知的请求。

### 4. 中：上传后的原始文件名更新不是原子操作

**代码位置**：

- `personalkb/workflow.py:129-130`
- `personalkb/web_app.py:277-281`

`import_file()` 使用临时 UUID 文件名创建并提交 source/task，随后 Web 层再单独执行：

```sql
UPDATE sources SET original_name=?
```

如果第二步数据库写入失败：

- API 返回失败，但资料和任务已经存在。
- 原始文件名仍是临时 UUID 名称。
- 用户重传相同文件会命中重复资料，且重复分支不会修复文件名。

**修复建议**：

- 将展示文件名作为参数传入导入流程。
- 在 `import_source` 的同一事务中写入，取消导入后的独立 `UPDATE`。
- 补充“首次提交后元数据失败、再次上传能正常恢复”的测试。

### 5. 低：登录页把几乎所有 HTTP 错误都显示为密码错误

**代码位置**：`web/src/main.jsx:74-81`

除 429 外，401、403、413、500、503 都显示“密码错误，请重试”。服务异常或 CSRF/Origin 问题时，会误导用户反复修改密码。

**修复建议**：

- 仅将 400/401 的 `invalid_credentials` 映射为密码错误。
- 429 显示限流提示。
- 其他状态显示服务或请求异常，不暴露内部细节。

## 三、Web UI 优化建议

| 优先级 | 方向 | 现状与建议 |
| --- | --- | --- |
| P1 | **问答首屏减负** | `rag.jsx:173-221` 中范围和检索模式始终展开，与 `phase-3u-frontend-contract.md:9` 的“范围和检索设置折叠”不一致。首屏保留问题、费用同意、生成按钮及必要覆盖提示；将范围/模式折叠为“全部资料 · 混合检索”。 |
| P1 | **移动端审核入口** | `style.css:47,202` 在 1050px 以下把审核区放到完整正文之后，长文下需要大量滚动。建议在标题附近增加“前往审核”锚点，并提供轻量审核状态入口；不要把整个审核表单移到正文前。 |
| P1 | **反馈靠近操作** | 审核错误和成功信息集中渲染在 `main.jsx:324`，但提交按钮在页面底部。移动端提交失败后，用户可能看不到顶部错误。审核反馈应在审核面板内同步显示，全局区域主要保留连接和会话错误。 |
| P2 | **扩大移动触控目标** | 通用控件高 36px，移动导航最低 32px，部分资料勾选区为 24px。建议手机端主要按钮、导航、页签和勾选标签提升至 40–44px；桌面保持现有紧凑密度。 |
| P2 | **收敛问答状态信息** | 索引状态、自动索引状态、覆盖率和诊断分散在多个区块。保留“当前范围能否回答”和异常原因，运维数据统一收进诊断区，减少主流程中的重复状态。 |

### 不建议的优化方向

- 不建议更换整体配色。
- 不建议将所有内容卡片化。
- 不建议增加装饰性渐变。
- 不建议压缩正文行宽。

这些调整不会解决当前主要交互问题，反而可能破坏已经形成的阅读密度和视觉一致性。

## 四、建议处理顺序

1. 修复历史版本保留规则。
2. 修复问答逐次费用授权。
3. 实现轮询串行化及响应次序保护。
4. 修复上传原子性。
5. 修复登录错误分类。
6. 优化问答首屏、移动审核和局部反馈。
7. 精修触控目标与状态信息展示。
