# PersonalKB UI设计与评审

项目位置：`D:/codex_project/My_RAG/PersonalKB`。项目内本文件为维护源；本机`~/.codex/skills/personalkb-ui-design/`是供发现使用的副本，修改时同步。优先遵循项目当前PRD和用户当次要求。

## 开始工作

先读项目`docs/PLAN.md`最新状态和当前设计简报：第二版用`docs/ui-redesign-v2-brief.md`，首版`docs/ui-design-brief.md`仅供历史对照。与`frontend-design` skill协作时，外部skill负责视觉/文案自检，本skill负责PersonalKB的审核/证据和阶段边界。设计和实现前先明确测试用例。不要为评审全仓扫描；保留与任务无关的数据、草稿、审核与索引状态。

先判断任务是设计样稿、正式接入还是评审。样稿必须标明演示数据，隔离真实业务写入和收费调用；用户批准样稿后才进入正式界面统一实施。批准设计不代表批准资料、模型输出或上线。

## 产品优先级

- 资料库：帮助找内容；标题、来源、主题、审核状态比文件名和内部ID重要。让搜索/筛选作用于有内容的主区域，空状态提供恢复入口。
- 详情：让人读懂材料并检查证据。正文主列、审核辅助区；HTML与视频显示各自真实适用的证据入口。技术信息和危险/付费操作降为次级入口。
- 审核：评分与明确批准分开；显示当前版本状态，修改后重审。设计不得暗示高分自动批准或把演示评分写入真实资料。
- 问答：首屏能提问，范围选择简洁，索引运维不挤占主流程。文章段落、正文编号脚注和来源证据延续已有可读性成果；不把检索候选当实际引用。
- 真实接入：保留版本/CAS、失效引用、无依据拒答、付费同意与任务恢复语义，不能为了简化UI隐藏这些边界。

## 设计与实施

先判断页面是操作工具还是宣传展示：PersonalKB当前三页属于操作/阅读工具。用户已否定第一版暖底/墨绿、大标题、英文眉题和口号的组合。当前按第二版简报使用中性笔记软件界面、紧凑导航/列表、普通中文标题和少量操作强调色；不要只换色沿用被否定的版式。颜色和间距等可调参数放有说明的tokens配置，具体主题仍可依据用户反馈调整。

布局必须服务资料密度、阅读和核对。先用本项目真实场景检查：能否一屏浏览当前四份演示材料、找到待审入口、同时核对正文和意见、直接提问并看来源？避免每页重复英文全大写眉题、泛用口号、超大英雄标题、装饰编号/箭头、整齐但无意义的卡片，以及为“去AI味”反向套用报纸/海报模板。技术名和文件原名中的英文可以正常保留。

每页只突出当前主动作；给次动作、危险动作、状态标识不同层级。避免资料列表很窄而右侧大面积空置、表单配置挤掉提问框、全文操作纵向堆叠、审批状态与文案矛盾等现存问题。

优先使用已有技术和本地资源；不因审美任务引入新运行时服务。现有8765主服务CSP要求同源外部JS/CSS；独立样稿不要覆盖正式入口或已有评分页。若需要构建，输出到隔离tmp目录，保留其他assets。

## 评审与交付

执行[评审清单](references/review-checklist.md)。结合实际页面截图与点击结果评审，不凭源码推断视觉通过。多Agent可用时，较复杂的设计安排独立评审，设计负责人判断并复核修复。

评审分两层：先检查是否像本项目的日常知识工具、是否仍有用户否定的模板感；再做功能/可访问性检查。工程通过或安装skill不代表视觉被本人认可。保存版本对照，不把第一版待确认状态写成批准。

已批准样稿接入正式前端时，必须做同页、同视口、对应状态的对照：先核对界面/正文/标题字号、字体栈、品牌/导航图标、顶栏/主区对齐，再检查筛选标签、列表状态日期列、阅读标签/审核分隔与问答行宽。保存两边截图及实际computed styles；仅复用配色、tokens名称或通过“不溢出”不能算设计还原。真实业务增加的控件与演示数据差异单独说明，禁止填充假主题/回答换取截图相似。功能验收与本人视觉确认分开记录；收到偏离反馈要重开视觉验收，不能沿用此前工程通过结论。

记录页面/视口/场景、问题影响与优先级、验证证据和剩余限制；将发现与建议区分。更新PRD版本（规格变化时）、PLAN、TodoList与CHANGELOG。交付可打开的预览、三页截图与需要本人确认的具体设计点，不把样稿通过写成生产验收通过。
